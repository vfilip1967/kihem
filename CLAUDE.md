# Kihem — instructions for Claude CLI

Read `README.md` and then `MEMORY.md` before changing this repository. They
are the product documentation and durable context. Keep both current when a
feature or an implementation decision changes.

## Safety and scope

- Preserve unrelated worktree changes. The repository can be deliberately
  dirty; inspect `git status` and stage explicit paths, never use reset/clean
  to make it tidy.
- The production app is `/var/www/kihem`, served by `kihem.service`. Runtime
  digital-score assets are intentionally outside Git in
  `/var/lib/kihem/digital-scores`; private source material and review records
  must stay private. Do not publish source scans, EZ fonts, Word files or
  unreviewed `.byzx` drafts.
- Treat Melodos HTML as untrusted and do not copy scripts or event handlers.
- A generated Byzantine score is never musically correct merely because it
  loads or plays. Preserve the source and require named psaltis visual and
  auditory review before changing a score to `verified`.

## Verification and deployment

Run the focused suite after changes to this area:

```bash
venv/bin/python -m unittest \
  tests.test_neanes_byzx_bridge tests.test_ez_word_neanes_draft \
  tests.test_digital_scores -v
```

To create a private `.byzx`, use the checked event draft and the local Neanes
checkout with `digital_scores/build_ez_neanes_byzx.py`. Do not hand-write a
generic `.byzx` JSON structure.

Deployment requires copying only the changed app/templates into `/var/www/kihem`,
installing the private asset with restrictive permissions in
`/var/lib/kihem/digital-scores`, then restarting `kihem.service`. Confirm the
service is active. Do not put review credentials, API keys or private assets
in Git.
